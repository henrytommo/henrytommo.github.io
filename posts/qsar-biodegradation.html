QSAR Biodegradation Prediction

September 2026

A little while ago, I followed a tutorial on writing up a simple graph neural network from scratch. I was keen to put these learnings about GNNs into chemical context, and at the time was reading some cool stuff about predicting the biodegradability of certain compounds using ML. A quick Google search found the QSAR dataset, and I jumped right in to try out my new GNN skills. However, my choice of dataset was probably more suited to a tabular model. The QSAR dataset already had those properties as part of the tabular dataset, and those properties calculated by "real" chemistry will probably outperform whatever relationships are found in my simple model. Regardless, it was a great learning experience.

I'll run through my process of this project, including my thoughts and mistakes I made along the way, along with what I'd do next time. Code can be found at qsar-biodegradation.

First, the dataset

The dataset, found here, contains 1055 molecules, described by 41 quantitative structure-activity relationship (QSAR) features and with a binary label of readily biodegradable (RB) or not readily biodegradable (NRB).

  • Biodegradation is tested by OECD Test no. 302:
    • biodegradation under aerobic conditions in dark/diffuse light by microorganisms
    • RB if 60% of theoretical oxygen demand or organics carbon is consumed/converted within 28 days (with degradation within a 10 day window after it first reaches 10%)
  • features contain things like:
    • num of heavy atoms
    • num quaternary C atoms
    • num of substituted benzenes
    • % of C atoms
    • num of halogens

i.e. - all 2D features. No stereochemistry: as this dataset shows molecules broken down by microorganisms, i.e. enzyme-using organisms, I assumed stereochem would be a good indicator due to the selective nature of enzymes. This led me down one rabbit hole investigating GINEConvs, but unfortunately only about 1% were stereoactive and therefore this didn't give the performance uplift I was hoping for.

First thoughts were that features such as number of halogens would be a good indicator of biodegradability (more halogens = less biodegradable). None of the features included any electronic properties, and although it's been a long time since I learnt about DFT, I was keen to look into it (and perhaps explore more in further projects). I mostly wanted a feature that could describe HOMO-LUMO gap, to try and give an idea of how reactive a molecule was, and in the process found some other potentially useful features. Additionally, the labels are calculated by % of oxygen used etc, so potentially some misclassifications if compounds are close to the boundary, so this was something to keep in mind. The class imbalance was about 34% RB and 66% NRB, so need to keep this imbalance in mind.

Next, data pipeline

Although this was a project designated as a GNN learning exercise, when I was reading around the QSAR dataset I saw that XGB and KNN models gave good results. I wanted to set up a data pipeline that would allow me to process the data for XGB, GCN and logreg in a reusable way, perhaps with a flag to denote graph data. This was the part of the project where Claude was most heavily involved, for going through the various approaches for the Dataset class I wanted to create.

As there were only about 1055 molecules, I wanted some kind of cross-validation/bootstrapping. Went with k-fold cross validation in the end (simpler stratification), but ran 5 folds 3 times to account for worse variance.

I wanted my Dataset class to:

  • be reusable across my 3 model types
  • be set up for k-fold cv
  • handle errors (although, ended up just dropping errors as the dataset was clean already)
  • handle adding extra features (xtb, rdkit)
  • allow for feature selection
  • have a robust scaling/transforming step that happened within each fold

I began experimenting with all 41 QSAR features, plus 9 xtb features and 3 rdkit features. Only later in my experimentation did I introduce simple feature ranking and subset selection (using xgb to select features for GCN - for ease).

I found a SMILES dataset corresponding to the QSAR dataset I already had, allowing me to create my GCN. The SMILES representations were used for the xtb calcs to generate the dft features, and also as the basis of the GCN. Each SMILES representation was converted to:

  • x: (n_atoms, 4), where the 4 features are:
    • atomic number (6 for carbon etc). This does mean that atomic number is continuous, whereas it should probably be categorical as there isn't really a linear relationship in atomic number
    • number of connections
    • formal charge
    • binary indicator is_aromatic
  • so, no info on type of bond (single, double). hence trying out GINEConv, with poor results

The Dataset class

The dataset class is a reusable way to set up the data for any of the three model experiments.

General

load
  • specify graph true/false
  • loads graph from SMILES if true, calculating xtb/rdkit features
  • else, doesn't load graph, but still builds xtb/rdkit feats
is_graph
  • self-explanatory
dims
  • property (read only)
  • just gets num features, calculated depending on graph or tabular
feature_frame
  • returns tab view of dataset, no matter if graph or not
  • used for ranking (GCN ranking uses xgb for simplicity), but takes from the GCN dataset to account for dropped rows etc
like
  • helper method to create a new dataset with same feature names and structure, but new data
  • used for the cv splits etc
  • uses mutable lists, fine for now but should flag this in the future

Splitting + scaling

holdout
  • returns tuple (train_data, test_data)
  • NO SCALING, only splitting
  • 80:20 split (and then train is split into train + val in another func)
  • Due to class imbalance, stratification was done on labels. note: no stratifying by skeleton structure, keeping simple for now.
  • reproducible
  • different splitting for tab and graph
scale
  • fits scaler on training set (never on val/test)
  • only persists for inference, otherwise discarded between the cv folds
transform
  • never called on training data, just applies the already fit scaler on val/test data
cv_folds
  • generator to give scaled (train, val) pairs
  • ONLY used on train and val, never test
  • splits training data into 5 folds and produces (train, val) pair for both
  • folds stratified by label
  • fit scaler on train, then applies to val, then discards so that the scaler isn't applied across folds. by keeping scaling within each fold, avoid leakage
  • sample is without replacement, so each fold is used for val once and train 4 times - hence running 3x with a random seed to try and get around this
subset
  • feature selection
  • cap and n feats

dxtb

Brief overview - I wanted to include some electronic feats, and from some minimal reading around, the dxtb python package seemed the quickest and easiest to use. I wanted mainly to have a feature that represented HOMO-LUMO gap, to help indicate how easily SET would happen (often the case for enzyme catalysed reactions), but there were other features that could be calculated too, so included these. It's a semi empirical quantum chemistry method - i.e. not too crazy compute time.

Features I added:

  • HOMO-LUMO gap for reactivity, given we are looking at molecules being broken down
  • wbo total, max: measure of bond multiplicity/strength. No features that described this yet, and as mentioned corresponds to how easy something may be to break down
  • dispersion energy - might give some info about polarisability
  • delta SCF feats:
    • ionisation potential - ease of oxidation
    • electron affinity - ease of reduction
    • electrophilicity
    • condensed fukui funcs: how reactive

These dxtb calcs took a little longer, so there is a cache so that the same feats don't have to be re-calculated on each experiment when the training data is the same. Also note: there were some crazy high vals for IP and EA, which were discarded.

Although these features ranked fairly high in feature importance, they didn't really push up the metrics. Likely being inferred elsewhere.

Model training and tuning

tune.py finds the best configs for the model (without taking too long). It finds the hyperparams, scaling method, and optionally how many features. Outputs are written to config/best_params.yml.

Process:

  • All tuning happens on train only, so set aside the test set
  • Create hyperparameter grid (capping at n features if there's a cap)
  • Random search: a full search over all possible combos would be huge. Random sampling may not give the best configuration, but it's much quicker to get to a good config with far fewer trials. Sorted by (mean) f1
  • For each sampled config, 3 partitions of 5 folds are tested
    • rank_features is called within the fold loop, so features are re-ranked separately per fold - no leakage
    • repeated cv x3 and take mean per param config
    • xgb feature ranking is used for GCN - quicker
  • Once best config is chosen, the actual feature list is produced by ranking on the full training set and taking top-N
  • outputs are written to config.yml

Quick aside - ModelSpec

  • A class that contains info about a model
  • Allows different types of models to train in the same pipeline - when setting up the class, can pick the relevant methods for the model.
  • This just means you can add a completely different type of model and it would still work with the pipeline.
  • Probably slightly overkill for just 3 models, but useful if trying loads of different models and makes the pipeline code a bit simpler, which would be easier for later maintaining (i.e., just need to know how one pipeline works, rather than 3, and the individual parts are much smaller and easier to look into)

Val_size

  • After best params have been chosen by cross validation, number of epochs and number of trees need to be found for gcn and xgb, respectively.
  • As the final fitting is on a bigger data set, can't use the stopping point from the cv - only use hyperparams
  • For xgb and gcn, val_size gives a 15% validation set for early stopping (e.g. if validation score stops improving)
  • GCN also has a patience loop, where if validation loss doesn't improve after 15 epochs it stops.

Comparing models

  • Once config has been found by tune.py, compare.py runs each model over 10 splits (80/20 train/test)
  • model is trained on that train set and scored against the test
  • Across all 3 models with all relevant metrics
  • However, xgb and logreg use the same seed (i.e. tested on the same set). As they use the exact same features, it means they can be compared like for like. As GCN uses graph features also, it's not really directly comparable.
  • The limitation here is that the 10 seeds are not independent - no folds. But on a fairly small dataset of ~1000 rows it allows the models to be trained on enough data.

Metrics

  • F1 score
  • Precision
  • Recall
  • ROC AUC
  • PR AUC

PR AUC included as well as ROC AUC - ROC AUC can inflate true negative, so include PR AUC.

Inference

Now we've looked through the data pipeline and model training. Next is inference. Instead of using a saved model, the inference pipeline trains a model based on the chosen configurations and infers using that. For now will keep this way as it doesn't take too long to train. If making multiple predictions, there's a predictor param that can be passed so that you're not re-fitting each time. This is probably the part that I would change, but as this was more of an experimental project it's ok for now.

Included in the inference part of the project is also an option for using ensemble methods. EnsemblePredictor can take the average of two models and predict using that - the ensemble averages the probabilities, not the labels. Due to the set up of the data pipeline, both models can share the same loaded dataset to avoid repeated processing time.

xgb + logreg ensemble gave similar performance to all 3 models in an ensemble, and as the GCN is slightly more complex it could be dropped.

Similar to training, for a new dataset, if there are molecules whose xtb feats fail, there will be no prediction for that molecule. But, the output csv will have the same number of rows as the input, and any molecules that fail are marked "abstain" for further investigation.

The SMILES data I used for this also contained 670 external molecules. Validating the model on these shows that both the xgb + logreg ensemble and the gcn match their internal CV metrics (ensemble F1 around 0.77, ROC AUC 0.92, and gcn around F1 0.79, ROC AUC 0.93), so that's a good sign that there wasn't too much overfitting going on. GCN is actually a little better than the ensemble for the external dataset, so perhaps it's capturing some structural features that transfer better to new molecules. Quite a small gain for a more complex model, but interesting nonetheless.

Read below for a summary of the above.

Data prep

  • ~1,055 molecules, binary target (RB / NRB), Mansouri 2013 dataset; class-imbalanced (~34% RB).
  • 41 precomputed QSAR descriptors as base features.
  • Stratified k-fold; scaling fit inside each fold (no leakage).
  • Dataset was fairly clean, drop rows with failed features (1,055 down to 1,050).
  • Added SMILES - molecular graphs for the GCN (structure + QSAR globals).

Feature engineering

  • +3 RDKit 2D descriptors: MolLogP, MolWt, TPSA (checked overlap first — none direct).
  • +6 xTB electronic descriptors via dxtb (GFN1-xTB, RDKit ETKDGv3+MMFF 3D): HOMO-LUMO gap, IP, EA, electrophilicity, Fukui±, WBO (total/max), dispersion -> 53 features total. Cached (xtb_features.csv) as they're slow to compute.
  • Leak-free per-fold feature ranking searched jointly with hyperparams; final cap at 20 features (GCN ranks via XGBoost importances — cheaper than GNNExplainer over folds).

Models & reasoning

  • XGBoost — strong tabular baseline, handles collinearity/nonlinearity, gives feature importances.
  • Logistic regression — interpretable linear baseline, L1/elastic-net for sparsity, class-balanced.
  • GCN — tests whether raw structure beats hand-made descriptors.

Mistakes / dead ends

  • Stereoisomer flags + GINEConv - thought this may give some insights as whatever enzymes are being used to break down these chemicals will likely be stereospecific. However, only about 1% were chiral, and the GINEConv gave worse results so that was scrapped.
  • GCN tuning "mirage": a config tuned to test F1 0.816 but delivered 0.783 across seeds → fixed by 3× repeated 5-fold CV.
  • 4 molecules with unphysical ΔSCF (IP up to ~1785 eV), so added physical-bounds guard, and dropped them.
  • Code stuff: xgboost must load before torch/dxtb (OpenMP clash) + OMP_NUM_THREADS=1.

Packages tried

  • dxtb (kept), RDKit, torch-geometric, xgboost, sklearn.

Key results / findings

  • All three models get about the same metrics, around F1 ≈ 0.78–0.79, ROC-AUC ≈ 0.92 — task is saturated / data-limited, not feature-limited (extra descriptors rank well but don't improve much).
  • Capping 53 → 20 (or 15) features costs nothing and makes everything simpler.
  • Errors only partly shared — 34% of misses are single-model; there were 97 molecules (9.2%) wrong for all three, both classes.
  • Ensemble (xgb+logreg soft-vote) beats every single model internally; GCN internally droppable.
  • External validation (670 held-out): both generalise, no overfitting; GCN slighlty better than the ensemble out-of-sample (learns something from 3D structure).
